# Entity, identity, provenance, and truth boundaries — Case 01

## Context

This decision note continues the Case 01 design work after agreeing the initial relationship primitives.

The goal is to define the minimum semantic model needed for the first happy-path experiment without prematurely implementing the LangChain pipeline or expanding into entity resolution, uncertainty handling, or a full private-client ontology.

The central distinction remains:

```text
ground_truth.json
    = what is actually true in the synthetic world

source.txt
    = documentary evidence about that world

expected_extraction.json
    = what an ideal extractor is justified in concluding from that evidence
```

## 1. Case 01 entity types

The initial entity types are:

```text
Person
Trust
```

A trust is modelled as an entity rather than metadata attached to a person because it has its own identity and independently participates in relationships with multiple entities.

For example:

```text
Alice -- settlor_of ------> Evergreen Family Trust
Bob   -- beneficiary_of --> Evergreen Family Trust
Carol -- beneficiary_of --> Evergreen Family Trust
```

If trust roles were stored only as attributes on people, the model would lose which trust a role relates to as soon as more than one trust exists.

## 2. Minimum entity information

For Case 01, the minimum information attached to an entity is:

- stable ID;
- entity type;
- canonical name.

No additional private-client attributes such as date of birth, nationality, address, tax residence, etc. are required to test the Case 01 hypothesis.

Relationships belong on graph edges rather than as attributes on entities.

For example, Bob should not have an entity attribute such as:

```text
role = beneficiary
```

because Bob could be a beneficiary of one trust, settlor of another, and trustee of a third.

Those facts are relationships between independently identified entities.

## 3. Stable identity is distinct from textual mention

Relationships should connect stable entity identities, not literal name strings.

Conceptually:

```text
SOURCE TEXT
"Alice Chen"

     ↓ extraction / resolution

ENTITY
person_001
name: Alice Chen

     ↓

RELATIONSHIP
person_001 -- parent_of --> person_003
```

This matters because future documents may refer to the same underlying person as:

- Alice Chen;
- Alice;
- Mrs Chen;
- Mrs Alice Chen;
- the settlor;
- his wife.

Those textual mentions may all refer to one entity.

### Case 01 simplification

Entity resolution is explicitly deferred.

Case 01 will make identity trivial by using consistent, unambiguous names throughout the source material.

The design nevertheless records the principle that:

> Entity identity is not philosophically equivalent to the text used to mention the entity.

This allows later entity-resolution capability to be added without changing the fundamental graph representation.

## 4. Ground-truth IDs and extracted IDs are independent

The extraction pipeline must not receive hidden ground-truth identifiers.

Conceptually:

```text
GROUND TRUTH                 EXTRACTION

gt_person_001                extracted_person_001
Alice Chen                   Alice Chen

      │                             │
      └──── evaluator matches ──────┘
```

Ground-truth IDs identify entities in the synthetic reality.

Extracted IDs identify entities reconstructed from source evidence.

The evaluator is responsible for determining correspondence between the two.

For Case 01, this matching can be deliberately simple because aliases and entity resolution are out of scope.

Whether IDs are generated by the LLM itself or assigned deterministically after extraction is an implementation decision and remains open.

## 5. Mentioned entities versus graph-relevant entities

We considered a future document containing an incidental person such as:

> The meeting was prepared by relationship manager Sarah Jones.

Sarah is a person mentioned in the source, but she may not participate in the family/trust graph.

This exposed an important future distinction:

> "Mentioned in a document" and "belongs in the relationship graph" are not necessarily equivalent.

Determining whether incidental people should become graph entities would introduce a new relevance-filtering/ontology problem.

### Case 01 decision

Do not introduce incidental people yet.

Every named person or trust in the Case 01 source should be graph-relevant.

A later benchmark case can deliberately introduce unrelated or differently related people and define the expected behaviour.

## 6. Provenance is mandatory for extracted relationships

Every extracted relationship must have provenance.

An extracted edge without provenance is not considered a valid extracted edge.

For example:

```text
Alice -- parent_of --> Bob
```

should be traceable to source evidence such as:

> Alice Chen and her son Bob Chen attended the meeting.

This supports both human auditability and evaluation of whether the LLM's relationship claim is actually grounded in source material.

## 7. Provenance uses source text, not generated justification

The LLM may identify/select evidence, but it should not invent a natural-language explanation and present that explanation as provenance.

Good evidence:

> Alice Chen attended with her son Bob Chen.

Generated explanation:

> Alice Chen is Bob Chen's mother.

The latter may be a correct interpretation, but it is not itself evidence from the source document.

Therefore the Case 01 provenance requirement is:

> Source document + exact supporting text selected from that document.

This also creates the possibility of deterministic validation later: supporting text claimed by the extractor can be checked against the actual source document.

## 8. Evidence is a first-class object

Because provenance is central to the project hypothesis, evidence should have its own stable identity rather than existing only as duplicated text embedded independently on every edge.

Conceptually:

```text
DOCUMENT
source.txt
   │
   ▼
EVIDENCE e_001
"Alice and David have a son, Bob."
   │
   ├── supports --> Alice parent_of Bob
   │
   └── supports --> David parent_of Bob
```

This allows one evidence item to support multiple relationships.

It also leaves room for a future relationship to be supported by multiple evidence items across multiple documents.

Evidence is **not** a Person/Trust graph entity. It is provenance about graph assertions.

## 9. Minimum evidence information

For Case 01, an evidence object needs:

- stable evidence ID;
- source document;
- exact supporting text.

Page numbers, paragraph identifiers, character offsets, bounding boxes, etc. are deferred until source formats or observed failures justify them.

## 10. Relationships reference evidence, not vice versa

The canonical reference direction is:

```text
Relationship --> evidence ID(s)
```

Evidence does not also maintain a duplicate list of relationships it supports.

Reverse views can be derived by querying relationships that reference a particular evidence item.

This avoids duplicated state that could become inconsistent.

The decision follows the same general principle used for inverse relationships:

> Store one canonical representation and derive the inverse view when needed.

## 11. No confidence or uncertainty field in Case 01

Case 01 deliberately contains explicit, uncomplicated evidence.

Adding fields such as:

```text
confidence: 0.94
```

would introduce unclear semantics without providing useful information for this benchmark.

An LLM-generated confidence number is especially questionable unless there is a defined calibration methodology.

Case 01 therefore has:

- no confidence score;
- no relationship status;
- no uncertainty vocabulary.

This does not imply uncertainty is unimportant.

A later benchmark should deliberately introduce language such as:

> Alice indicated that Sophie may be added as a beneficiary.

That observed requirement can then drive a concrete decision about abstention, status, uncertainty, or another representation.

## 12. Ground truth must not contain extraction provenance

A key distinction emerged when considering the shape of `ground_truth.json`.

Ground truth represents reality itself.

If Alice is Bob's parent, that fact is true in the fictional world independently of whether any source document mentions it.

Therefore a ground-truth relationship should not contain evidence IDs merely because extracted relationships do.

Conceptually:

### Ground truth entity

- ID;
- name;
- type.

### Ground truth relationship

- source entity ID;
- relationship type;
- target entity ID.

### Expected extracted relationship

- source entity ID;
- relationship type;
- target entity ID;
- supporting evidence ID(s).

### Evidence

- evidence ID;
- source document;
- exact supporting text.

This preserves the boundary:

```text
truth
  ≠
evidence about truth
  ≠
conclusions justified by evidence
```

Case 01 may happen to have the same six relationship facts in ground truth and expected extraction because every fact is explicitly evidenced, but the representations remain intentionally different.

## 13. Current Case 01 semantic model

Without committing to an exact JSON schema yet, the current model is:

```text
ENTITY
- stable identity
- type
- canonical name

RELATIONSHIP (ground truth)
- source entity
- relationship type
- target entity

RELATIONSHIP (expected extraction)
- source entity
- relationship type
- target entity
- evidence reference(s)

EVIDENCE
- stable identity
- source document
- exact supporting text
```

## 14. Deliberately deferred

Case 01 does not yet solve:

- aliases/entity resolution;
- incidental named people;
- relevance filtering;
- uncertain or proposed relationships;
- historical relationship state;
- confidence calibration;
- multiple-document evidence aggregation;
- page/paragraph/character-level source locations;
- complex private-client entity types;
- richer relationship primitives beyond those already agreed.

These should be introduced only when later cases demonstrate the need.

## Next step

The semantic boundaries are now sufficient to begin designing `ground_truth.json`.

The next task is to translate the agreed fictional world into the smallest JSON representation of:

- entities;
- ground-truth relationships;

without leaking source-document evidence into the hidden truth fixture.
